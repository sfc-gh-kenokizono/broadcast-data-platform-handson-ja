# 放送データ基盤ハンズオン

**5局の視聴記録を取り込み、整え、グラフとAIから使えるようにする教材です。**

受け取った記録を、そのままグラフにしてよいのでしょうか？
同じ「ニュース」でも ` news ` と `NEWS` が混ざっていたら、別のジャンルとして集計されてしまいます。
また、同じ端末が2つの局を見たとき、局別の端末数を足すと二重に数えてしまいます。

このハンズオンでは、こうした点を確認しながら、データの取込から分析までを順番に体験します。
操作はSnowflakeのブラウザー画面 **Snowsight** が中心です。コードとデータは用意してあります。

## 最初に開くファイル

**[第1章 セットアップ](docs/01_setup.md)から始めてください。**

まだ教材のGit Workspaceがなくても大丈夫です。
最初のSQLは、GitHubで直接開けます。

**[sql/01_setup.sql を開く](https://github.com/sfc-gh-kenokizono/broadcast-data-platform-handson-ja/blob/main/sql/01_setup.sql)**

1. 第1章の[実行前の確認](docs/01_setup.md#実行前の確認)で、利用アカウントと管理者の案内を確認します。
2. 講師から `F1_SIGNAL_V2` 版の公開案内を受けたら、上のSQLをSnowsightへ貼り付け、第1〜5節を順に実行します。
3. 第1章の[Git Workspace作成手順](docs/01_setup.md#受講用git-workspaceを作る)に沿って、教材を自分の作業場所へ取り込みます。
4. 作成したWorkspaceで [sql/02_load_parquet.sql](sql/02_load_parquet.sql) を開き、第1章に沿って検査・取込ブロックと末尾の版記録SELECTを実行します。

GitHubのリンクは公開済みの `main` を開きます。ローカルの変更はpushされるまで表示されません。
データは公開済みのデータ専用コミット `8a6f0cc234b30c3b54a4a63d68890bb7cb9f8887` の `/commits/8a6f0cc234b30c3b54a4a63d68890bb7cb9f8887/data/` から読み込みます。`F1_SIGNAL_V2` はデータ版と内部ステージのフォルダ名で、Gitタグではありません。タグは公開しません。固定コミットを取得できない場合は停止し、`main` などへ変更しません。
リンク先が旧版の場合や、既に旧データをロードした環境では、先へ進まず講師へ確認してください。
同じ端末IDでも旧データと新データを混ぜることはできません。

### データはどこを通る？

```text
各局のファイル（Parquet / 内部ZSTD圧縮）
   ├─ NW01用WH → 整形 → テスト → NW01の集計表 → テスト
   ├─ NW02用WH → 整形 → テスト → NW02の集計表 → テスト
   ├─ NW03用WH → 整形 → テスト → NW03の集計表 → テスト
   ├─ NW04用WH → 整形 → テスト → NW04の集計表 → テスト
   └─ NW05用WH → 整形 → テスト → NW05の集計表 → テスト
                                ↓ 全局成功後
                    共通WHで5局の集計表を統合 → テスト
                                ↓
                       COMMON.VIEWING_DAILY（日次実績）
                         ├─ 学習・登録・予測 → ML.PREDICTIONS
                         ├─ Streamlitで実績とF1在籍確率を見る
                         └─ 指標の定義 → Agent → CoWorkで実績を質問
                       COMMON.MINUTE_AUDIENCE（分内視聴端末数）
                         └─ Streamlitで分単位の推移を見る
```

**原本を先に全部まとめるのではなく、各局で整えてからまとめます。**
ウェアハウス（WH）はSQLの計算担当です。保存先のDB・テーブルとは別です。
局ごとの計算を分けることで、どの局の処理に計算資源を使ったかを確認しやすくします。
5本の局別処理は各4モデル・15テスト、最後の共通処理は2モデル・6テストです。
合計22モデル・81テストで、日次マートと分単位マートをそれぞれ統合します。

## 使うデータ

架空の20,000台のテレビによる、2026年5月1日〜7月31日（92日間）の視聴記録です。
1台を1つの合成世帯に対応させ、世帯構成を考慮して新しく生成しました。
旧教材の番組マスタ・放送予定を利用していますが、**旧CSVの視聴ログをそのまま移した無損失変換ではありません。**

1行は「いつから、いつまで、どのジャンルを見たか」という1回の記録です。
同じ端末IDは、局をまたいでも同じ端末を表します。端末を照合する作業は済んでいる想定です。

入力は5局合計1,050,648行です。重複と不正区間を除くと1,050,000件、日次集計は1,045,120行になります。
視聴区間を分単位に展開すると13,532,927行、それを局・分ごとに集計すると548,535行です。
これらはV2配布データをローカルとSnowflakeで照合した件数です。総視聴時間は約12,511,642.266667分で、分単位へ展開した行数とは異なります。
2026-09-18の実行で照合済みです。浮動小数点の計算や合計には丸めがあるため、時間は第2章の許容誤差内で比較します。

**分内視聴端末数**は「その1分のどこかで視聴していたテレビの台数」です。
ある瞬間に同時視聴していた台数でも、視聴者の人数でもありません。局別の値を足して全局のリーチにはできません。

第3章の `TV_F1_PRESENCE_MODEL` は、「テレビに対応する合成世帯にF1（20〜34歳の女性）が在籍するか」を推定します。
これは期間中に変わらない世帯の設定であり、**今見ている人の特定や、人数の推定ではありません。**
正解があるのは2,000台（在籍あり344台）、残り18,000台の正解は `NULL` のままです。
V2では、学習の違いを観察しやすいように、世帯構成と視聴傾向の関係を意図的に強めています。**実際の世帯属性をこの精度で推定できるという意味ではありません。**
学習1,200台・調整用400台・最終評価400台を分け、確率を補正したロジスティック回帰を使います。調整用データだけで選んだ判定境界は0.46、最終評価のROC AUCはローカル・Snowflakeとも表示桁で0.988353です。評価の読み方は第3章で扱います。初期モデル版は `V2`、同版が既存なら未使用の `V3` などを選びます。

データの限界：F1在籍ありの合成世帯は「若い女性の単身世帯」と「若いカップル世帯」の2種類の生成テンプレートだけです。他の世帯構成への適用性能や世帯間の公平性は検証していません。高い評価値は、この限定した教材データ内の結果として読みます。

## 必須と補足の区別

- **本編**：第1〜5章。StreamlitはWHで動かす推奨手順を使います。
