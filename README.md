# 放送データ基盤ハンズオン

**5局の視聴記録を取り込み、整え、グラフとAIから使えるようにする教材です。**

受け取った記録を、そのままグラフにしてよいのでしょうか？
同じ「ニュース」でも ` news ` と `NEWS` が混ざっていたら、別のジャンルとして集計されてしまいます。
また、同じ端末が2つの局を見たとき、局別の端末数を足すと二重に数えてしまいます。

このハンズオンでは、こうした点を確認しながら、データの取込から分析までを順番に体験します。
操作はSnowflakeのブラウザー画面 **Snowsight** が中心です。コードとデータは用意してあります。

> **確認状況：新しい演習環境で、Workspaceから各章を進める画面操作を確認予定です。通し操作は未検証です。講師の開始案内を受けてから進めてください。**

## 最初に開くファイル

**[第1章 セットアップ](docs/01_setup.md)から始めてください。**

GitHubの教材は用意済みです。**自分でGitHubリポジトリを作る必要はありません。** 最初のSQLはGit Workspaceを作る前に開けます。

| 順番 | 操作 | 次へ進む条件 |
|---|---|---|
| 1 | [実行前の確認](docs/01_setup.md#実行前の確認)を読む | 演習用アカウントと管理者の案内を確認 |
| 2 | [sql/01_01_setup.sql](https://github.com/sfc-gh-kenokizono/broadcast-data-platform-handson-ja/blob/main/sql/01_01_setup.sql)をSnowsightへ貼り付け、第1〜5節を実行 | 第5節の `LIST` が成功し、8個のParquetが見える |
| 3 | [Git Workspaceを作る](docs/01_setup.md#受講用git-workspaceを作る) | `main` の教材ファイルが開ける |
| 4 | Workspaceで [sql/01_02_load_parquet.sql](sql/01_02_load_parquet.sql)を開き、第1章に沿って実行 | 初回のファイル準備と8本の `COPY INTO` が成功し、末尾SELECTの8表の件数が一致 |

| Gitに関係するもの | いつ用意する？ | 用途 |
|---|---|---|
| GitHubリポジトリ | 配布元として作成済み | 教材コードとデータの配布 |
| SnowflakeのGit Repository `BCAST_PLATFORM_REPO` | `sql/01_01_setup.sql` 第5節が作成 | SQLからデータを読み込むための接続先 |
| 自分用のGit Workspace | 第5節の `LIST` 成功後、Snowsightで作成 | SQL・dbt・Notebook・アプリのファイルを開く作業場所 |

取込元は `main` の `/branches/main/data/`、データ版は `F1_SIGNAL_V2` です。初回に `FETCH` → `COPY FILES` → 内部ステージの `LIST` で8ファイルを準備し、8本の `COPY INTO` でRAWへ読み込みます。**演習中は配布元・ステージのファイルを変更しません。** 取得できない場合は停止し、講師へ確認します。

同じ変更されていないファイルを同じ表へ再度 `COPY INTO` すると、Snowflakeがロード済みと判定できる間はスキップされます。再実行では `COPY FILES` を繰り返さず、[第1章の再実行手順](docs/01_setup.md#もう一度実行するとき)に従います。既存環境がある場合も、データを削除せず講師へ確認してください。

### データはどこを通る？

```text
各局のファイル（Parquet / 内部ZSTD圧縮）
   ├─ NW01用WH → 整形 → テスト → NW01の集計表 → テスト
   ├─ NW02用WH → 整形 → テスト → NW02の集計表 → テスト
   ├─ NW03用WH → 整形 → テスト → NW03の集計表 → テスト
   ├─ NW04用WH → 整形 → テスト → NW04の集計表 → テスト
   └─ NW05用WH → 整形 → テスト → NW05の集計表 → テスト
                                ↓ 全局成功後
                    共通WHで5局の集計表を統合 → テスト
                                ↓
                       COMMON.VIEWING_DAILY（日次実績）
                         ├─ 学習・登録・予測 → ML.PREDICTIONS
                         ├─ Streamlitで実績とF1在籍確率を見る
                         └─ 指標の定義 → Agent → CoWorkで実績を質問
                       COMMON.MINUTE_AUDIENCE（分内視聴端末数）
                         └─ Streamlitで分単位の推移を見る
```

**原本を先に全部まとめるのではなく、各局で整えてからまとめます。**
ウェアハウス（WH）はSQLの計算担当です。保存先のDB・テーブルとは別です。
局ごとの計算を分けることで、どの局の処理に計算資源を使ったかを確認しやすくします。
5本の局別処理は各4モデル・15テスト、最後の共通処理は2モデル・6テストです。
合計22モデル・81テストで、日次マートと分単位マートをそれぞれ統合します。
81テストは、5局と共通処理の計6回の `build` に含まれて自動実行されます。81回の手動操作ではありません。

## 使うデータ

**すべて教材用の合成データです。実際の視聴ログではありません。** 番組マスタ・放送予定と、架空の世帯構成をもとに生成しています。

| 項目 | 内容 |
|---|---|
| 対象 | 5局、テレビ20,000台。1台につき1つの合成世帯 |
| 期間 | 2026年5月1日〜7月31日（92日間） |
| 視聴記録の1行 | 「いつから、いつまで、どの局・ジャンルを見たか」の1区間 |
| 端末ID | 局をまたいでも同じIDは同じテレビ。照合済みの想定 |
| 配布形式 | Parquet 8個：局別ログ5、番組マスタ、放送予定、ラベル |
| データ版 | `F1_SIGNAL_V2` |

### 加工すると件数はどう変わる？

| 段階・指標 | V2配布データの期待値 |
|---|---:|
| 入力（5局のRAW合計） | 1,050,648行 |
| 重複・不正区間を除いた視聴記録 | 1,050,000件 |
| 日次集計 | 1,045,120行 |
| 視聴区間を分単位に展開 | 13,532,927行 |
| 局・分ごとの集計 | 548,535行 |
| 総視聴時間 | 約12,511,642.266667分 |

総視聴時間と、分単位へ展開した行数は別の値です。時間は丸めを考慮し、[第2章](docs/02_dbt.md)の許容誤差内で比較します。

> **分内視聴端末数**は「その1分のどこかで視聴していたテレビの台数」です。ある瞬間の同時視聴台数でも、視聴者の人数でもありません。局別の値を足して全局のリーチにはできません。

### 機械学習で何を推定する？

| 項目 | 内容 |
|---|---|
| 推定対象 | 合成世帯にF1（20〜34歳の女性）が在籍するか。期間中は変わらない世帯の設定 |
| 正解あり | 2,000台：在籍あり344台、在籍なし1,656台 |
| 正解不明 | 18,000台。正解は `NULL` のまま。0にはしない |
| データの分割 | 学習1,200台・調整用400台・最終評価400台 |
| モデル | 確率を補正したロジスティック回帰 `TV_F1_PRESENCE_MODEL` |
| 判定境界・評価 | 調整用データだけで選んだ境界0.46、最終評価ROC AUCの参考値0.988353 |
| モデル版 | 初期版 `V2`。同版が既存なら未使用の `V3` などを選択 |

評価の読み方は[第3章](docs/03_mlops.md)で扱います。

> **今見ている人の特定や、人数の推定ではありません。** V2では学習の違いを観察しやすいように、世帯構成と視聴傾向の関係を意図的に強めています。実際の世帯属性をこの精度で推定できるという意味ではありません。

> **データの限界：** F1在籍ありは「若い女性の単身世帯」と「若いカップル世帯」の2種類の生成テンプレートだけです。他の世帯構成への適用性能や世帯間の公平性は検証していません。高い評価値は、この限定した教材データ内の結果として読みます。

## 必須と補足の区別

- **本編**：第1〜5章。StreamlitはWHで動かす推奨手順を使います。
- **任意の補足**：[基本SQL・Cortex Search・定期実行の考え方](supplemental/README.md)。省略しても本編を完了できます。
- **講師デモのみ**：App Runtime。受講者は作成しません。現在は未実装で、配布資材には含めていません。
- **対象外**：DCR、外部モデルファイルの持ち込み、高度な自動再学習。

## フォルダの見方

`sql/`の先頭の番号は章番号です。同じ章で2本使う場合は、`01_01_setup.sql` → `01_02_load_parquet.sql` のように章内の順番も付けています。第3・4章はNotebookとアプリを使うため、対応するSQLファイルはありません。

| フォルダ | 入っているもの | 使う場面 |
|---|---|---|
| `docs/` | 説明と操作手順、Agentへ貼り付ける文章 | 各章で読む |
| `sql/` | 環境準備・取込・確認・AI設定・後片付けのSQL | 手順で指定された箇所を実行 |
| `data/` | 内部ZSTD圧縮の8個のParquet（局別5、番組マスタ・放送予定、ラベル） | 第1章で取り込む |
| `dbt/` | 整形・集計のSQLとデータテスト | 第2章で使う |
| `notebooks/` | 学習から予測保存までのNotebook1本 | 第3章で実行 |
| `app/` | Streamlit用の3ファイル | 第4章で配置 |
| `supplemental/` | 任意の追加教材 | 本編の後、必要に応じて使う |
