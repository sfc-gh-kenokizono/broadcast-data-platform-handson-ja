# 1. 視聴データを取り込む準備

## 目的

5局から届く「いつから、いつまで視聴したか」という記録を、局ごとのRAWテーブルへ読み込みます。RAWは受け取った原本の保管場所です。この章では表記の揺れを残し、次章のdbtで整えます。

> **なぜ環境を分ける？** 局ごとの処理を別々の計算環境（ウェアハウス）で動かすと、どの処理に計算資源を使ったかを確認しやすくなります。局横断の処理には共通ウェアハウスを使います。

公開リポジトリの生成済みParquetを使います。データの生成やローカルPCでの準備作業は不要です。Git Workspace経路の一連の動作確認は未完了のため、講師の案内に従って進めてください。

## データの約束

- 全データは架空です。実在の放送局、人物、世帯、視聴者調査とは関係ありません。
- 期間は2026年7月1日から7月30日。日時は日本の壁時計時刻を想定し、タイムゾーンを持たない型で保存します。UTC変換はしません。
- 端末IDは全局共通の `D0001` から `D0200`。教材を簡潔にするため、IDの突合は済んでいる想定です。
- 1台1日3区間、全局合計18,000行です。各局3,600行で、全30日・全200台が各局に登場します。視聴しない時間は行がありません。
- 同じ端末の区間は局をまたいでも重なりません。日付をまたぐ区間は生成しません。
- `GENRE` は前後の半角スペース、小文字、全角大文字を含みます。整形後は `NEWS / DRAMA / VARIETY / ANIME / SPORTS` の5種類です。
- 全角は `ＮＥＷＳ→NEWS`、`ＤＲＡＭＡ→DRAMA`、`ＶＡＲＩＥＴＹ→VARIETY`、`ＡＮＩＭＥ→ANIME`、`ＳＰＯＲＴＳ→SPORTS` の明示的な置換だけを想定します。汎用のUnicode正規化ではありません。
- 整形後に不正な行は残らない設計です。異常値の実演は原本を書き換えず、テスト用の一時データで行います。

### 教育用の正解ラベル

`TARGET_SPORTS_FAN` はスポーツへの関心を模した架空の0/1ラベルです。年齢・性別などの人口統計属性でも、実在人物の属性でもありません。

固定の100台 `D0001..D0100` のみ `LABEL_AVAILABLE = TRUE` で、正解0が50台、1が50台です。残り100台の正解はParquetにも `NULL` として保存します。不明を0に置き換えないでください。

視聴習慣にはラベルとの緩い関連があります。ただし15%の確率で習慣側のクラスを反転し、端末ごとのばらつきと視聴ごとの偶然も加えています。「スポーツを見たら必ず1」とはなりません。既知・未知の端末は同じ生成ルールです。局の割り当てや区間数はラベルで変えません。

学習・評価は既知100台を端末単位で分け、両クラスを含むよう層化分割します。`DEVICE_ID` は結合キーであり、モデル入力にしません。`LABEL_AVAILABLE` と `TARGET_SPORTS_FAN` も説明変数に含めません。学習・評価の具体的な分割と検証はML章の担当です。この章ではモデル学習を行いません。

## 配布データを使う

受講者は `data/` にある生成済みの6個のParquetを使います。データ生成の操作、ローカルPython、Cortex Code Desktopは不要です。生成コードは教材作成者が別管理しています。

日時はParquetの `timestamp[us]`、ラベルはBooleanとNULLを許す整数です。ZSTDはParquet内部の圧縮であり、外側にgzipなどを重ねません。

## 実行前の確認

- 講師はSQLを実行する前にアカウントを確認します。旧教材や業務用の環境で実行しないでください。
- 初期準備は `ACCOUNTADMIN` を使います。以降は `BCAST_PLATFORM_ENGINEER_ROLE` を使います。
- この固定名を使う環境は1アカウントに1組です。複数の参加者が同じアカウントで独立実施する場合、講師による全教材を通した命名調整が必要です。
- Snowflake側のGit連携、利用機能、パッケージの提供状況を事前確認します。利用リージョンや管理ポリシーによる制限は実環境で確認してください。
- リポジトリURLは `https://github.com/sfc-gh-kenokizono/broadcast-data-platform-handson-ja.git`。`main` ブランチの `data/` に6個のParquetがあることを確認します。

## SQL

### 0. 最初にSQLを開く

まだGit Workspaceがない場合は、GitHubの `sql/01_setup.sql` を開き、内容をSnowsightのSQLワークシート、または自分のWorkspace内の新しいSQLファイルへ貼り付けます。管理者の案内に従って、次の専用環境の準備を行います。

### 1. 専用環境を作る

`sql/01_setup.sql` をセクションごとに実行します。最初に10スキーマと6ウェアハウスを作り、必要な作成権限と参照権限を付与します。既定ロール・既定ウェアハウスは変更しません。

**ロール付与先の確認:** セクション1の `CURRENT_USER()` はSQLを実行しているユーザーです。この付与部分は、管理者と受講者が同じ1人のユーザーである単独学習を想定しています。管理者が実行しても、別の受講者へ自動でロールは付与されません。同じSnowflakeアカウントを複数ユーザーで使う場合は、管理者が実在する各受講者のユーザー名と担当（作成者／閲覧者）を確認し、必要な教材ロールを受講者ごとに付与してください。ユーザー名を推測したり、架空のユーザーを作ったりしません。受講者は自分に付与されたロールを確認してから次へ進みます。

**実行基盤の範囲:** このセットアップは compute pool の作成・USAGE 付与や Workspace 開発環境の準備を行いません。第4章の必須経路は、共通WHで動く **経路B（warehouse runtime）** を推奨します。経路A（Git Workspace／container runtime）は補足です。選ぶ場合は、講師が利用可能な compute pool・権限・ランタイムの前提を別途確認します。共通WHだけで経路Aも準備済みとはみなしません。

エンジニアはRAWの取り込み、局別・共通dbt、ML、アプリとAI用オブジェクトを作成できます。RAWテーブルと内部ステージはエンジニア自身が作成・所有するため、その後の読取・書込ができます。アナリストにRAW・局別・MLスキーマへの権限は付与しません。共通集計とMARTを参照する権限だけを準備します。アプリ、セマンティックビュー、Agentの個別利用権限は、それぞれを作成する章で付与します。MLの正解ラベルをアプリへ公開しないでください。

各局のdbtは対応する `BCAST_PLATFORM_NW01_WH` から `BCAST_PLATFORM_NW05_WH` を明示選択し、テストも同じWHで実行します。全5局が合格してから `BCAST_PLATFORM_COMMON_WH` で共通集計へ進みます。詳しくはdbt章を参照してください。この章のロードは共通WHを使うため、局別dbtの計算とは区別します。

`CREATE ... IF NOT EXISTS` は既存の中身を初期化しません。同名オブジェクトがあっても定義・所有者・権限が一致するとは限りません。別用途の同名環境があるときは停止してください。

**セクション5で公開リポジトリに接続します。** Git用の秘密情報は不要です。Git API統合の許可URLはこの教材だけに限定します。

### 受講用Git Workspaceを作る

SQLで作るGitリポジトリオブジェクトは、ファイルを読み込むための接続先です。第2章以降でファイルを開くGit Workspaceとは別なので、次も行います。

1. 教材ロールの付与を確認し、`BCAST_PLATFORM_ENGINEER_ROLE` を選びます。
2. Snowsightの **Projects → Workspaces → From Git repository** を開きます。新規作成メニューの中にある場合もあります。
3. URLに `https://github.com/sfc-gh-kenokizono/broadcast-data-platform-handson-ja.git`、API統合に `BCAST_PLATFORM_GIT_API`、ブランチに `main` を指定します。公開リポジトリなのでGit用シークレットは不要です。
4. 自分用のWorkspaceを作り、名前を `broadcast-data-platform-handson-ja` にします。別の名前にした場合は第2章のSQL内のWorkspace名も合わせます。
5. ファイル一覧に `README.md`、`dbt/dbt_project.yml`、`notebooks/03_mlops.ipynb` が見えることを確認します。ここからはこのWorkspace内のSQLと教材を開きます。

画面で必要な項目を選べない場合は講師へ確認してください。SQLのGitリポジトリ作成が成功しただけで、Workspaceも作成済みとは判断しません。

### 必須Notebookの実行準備

第3章のNotebookには、共通WHとは別にPython実行用compute poolが必要です。これはStreamlitの補足経路だけの前提ではありません。演習開始前に、講師が利用するpool名・runtime名・必要パッケージと利用権限を準備して案内します。

WorkspaceでNotebookを開き、接続画面から案内されたPython環境を選択できることを確認します。講師は利用者ごとに接続と指定ロールでの実行可否を確認してください。pool・runtimeが未指定、または接続できない場合は第3章を開始しません。教材SQLだけでこの準備が完了するわけではありません。

### 2. 内部ステージへ移し、RAWへ読み込む

`sql/02_load_parquet.sql` を区切って実行します。Gitのファイルは `COPY FILES` で内部ステージ `BCAST_PLATFORM_RAW_STAGE` へ移してから読み込みます。

**最初の停止点:** `COPY FILES` の結果が6行で、ファイル名が想定どおりか確認します。このコマンドは存在しない指定ファイルをスキップします。内部ステージに古いファイルが残っている場合、`LIST` で6個見えるだけでは今回のコピー成功の証明になりません。必ず今回のCOPY結果を確認してください。

ファイル形式 `BCAST_PLATFORM_PARQUET` は `TYPE = PARQUET / COMPRESSION = AUTO / USE_LOGICAL_TYPE = TRUE / USE_VECTORIZED_SCANNER = TRUE` です。Parquetの読み込み用COMPRESSION設定に `ZSTD` を直接指定せず、内部圧縮を自動検出します。タイムゾーンなしのマイクロ秒論理型を解釈し、さらに `::TIMESTAMP_NTZ` を明示します。

**次の停止点:** サンプルSELECTで日時が2026年7月の値として読めることを確認します。整数や意図しない日時なら先へ進まず、Parquetとファイル形式を確認します。

各 `COPY INTO` は6列または3列を順番まで明示します。`MATCH_BY_COLUMN_NAME` は変換SELECTと併用しません。`TRY_*` で型変換エラーをNULLに隠したり、`ON_ERROR = CONTINUE` で失敗行を捨てたりしません。いずれかの文が失敗したらその時点で停止します。全6文は一括トランザクションではなく、先に成功したテーブルは残ります。

### 3. 再実行の扱い

`FORCE = FALSE` により、同一ファイルの再ロードはSnowflakeのロード履歴に従ってスキップされます。原本が同じで履歴が有効な間の再実行を想定しています。履歴の有効期間を越えた場合や、同名ファイルを再生成して内容を変更した場合の無条件な重複防止は保証しません。

`FORCE = TRUE` への変更や、件数を合わせるための部分的な削除はしないでください。教材データを変更する場合は、講師が依存するdbt・MLの成果物も含めてリセット方針を決めます。

## 動作確認

ロードSQL末尾の件数確認を使います。各局3,600行、ラベル200行、端末200台、既知100台、未知NULL100台、クラス0/1各50台、未知への正解漏れ0台が期待値です。初回COPY結果のエラー件数も0であることを確認します。再ロードでは「File was loaded before」とスキップされ、件数が増えないことを確認します。

## データの注意点

このデータは処理の流れを学ぶための教材です。実際の視聴率調査の代表性やモデル精度を保証しません。また、局別WHで計算は分かれますが、この演習のエンジニアロールは全局のデータを扱えます。

## 後片付け

`sql/cleanup.sql` はこの新教材のデータベース全体、6ウェアハウス、Git API統合、2ロールを削除します。DB内のモデルや公開済み Streamlit／Agent オブジェクトも削除対象です。通常手順と一緒に実行せず、教材が不要になり、共同利用者への影響と退避を確認してから使います。旧教材のデータベースとWHは対象に含めていません。

**Workspace 開発アプリは別に片付けます。** 第4章の経路Aで起動した私用の開発アプリは、公開済み Streamlit オブジェクトとは別です。SQL実行前に各利用者が Workspace 側で対象の開発アプリを停止し、不要になったこの教材専用のアプリ／ソースを削除します。専用 Workspace 自体の削除は、退避済みで他の作業に使っていない場合だけ行います。DB削除だけで開発アプリや Workspace も停止・削除されたとはみなさず、Workspace 側でも残存・稼働状態を確認してください。

このSQLは compute pool を削除・停止しません。アカウント既定・システム管理・他用途と共有する compute pool は対象外です。教材のために別途用意した専用 pool があれば、管理者が他の利用がないことを確認し、教材SQLとは別の管理手順で片付けます。
