# 第3章 MLOps体験: 合成世帯のF1在籍を推定する

> 同梱Notebookは20,000台・F1予測版です。旧200台版の表とは互換性がありません。第1章の移行上の注意を確認してください。新NotebookのRegistry・WH推論の実機確認状況は、後述の検証範囲を参照してください。

第2章で作った5局の共通マートを使い、**テレビに対応する架空の世帯にF1層がいるか**を予測します。この教材のF1層は20〜34歳の女性です。評価指標の「F1スコア」とは別の意味です。

テレビ1台を1つの合成世帯に対応付けています。複数の世帯員の視聴が混ざるため、世帯の特徴と、いまテレビを見ている人は同じではありません。今回のラベルは期間中に変わらない世帯の在籍情報です。

> すべて教材用の合成データです。現在の視聴者、個人の年齢・性別、人数を特定するものではありません。確率を合計して人口や実際のF1視聴者数に換算することもできません。

**学習・評価したモデルに名前と版を付け、その登録版で確率を計算し、使用した版とともに保存する**ところまで体験します。動作が成功することと、予測品質が十分であることは別です。このデータで得られた低い精度も、そのまま読み解きます。

## まず、何をするのか整理する

| 言葉 | この章での意味 |
|---|---|
| 特徴量 | 予測のヒントにする数値。ジャンルごとの視聴時間割合など |
| ラベル | 合成世帯にF1層がいれば1、いなければ0。不明はNULL |
| パネル | 正解ラベルを公開する2,000台のテレビ |
| 学習 | 正解付きの例から予測の仕組みを作ること |
| ホールドアウト | 学習に使わず、最後の採点に取っておく端末 |
| 推論 | 学習済みモデルで新しい入力の予測値を計算すること |
| Model Registry | モデルに名前・版・評価値を付けて保管する場所 |
| MLOps | モデルの版や利用結果を管理する取り組み |

ここでのモデルは学習済みの予測器です。第2章のdbtモデル（表を作るSQL）とは異なります。

```text
2026年5〜7月の視聴実績 → テレビごとに12項目へ集計
                                  ↓
                  正解付き2,000台を1,600台 / 400台に分割
                                  ↓
                        固定モデルの学習・評価
                                  ↓
                    TV_F1_PRESENCE_MODEL / V1 を登録
                                  ↓
                      登録版で20,000台の確率を計算
                                  ↓
                       許可後に確率・判定・版を保存
```

## 1. Notebookを開く

1. 第2章で5局と共通マートのbuild・テストがすべて成功したことを確認します。
2. SnowsightのGit Workspaceで `notebooks/03_mlops.ipynb` を開きます。
3. 講師が案内するPython実行環境に接続します。参加者のローカルPCでは実行しません。
4. 実行ロールを `BCAST_PLATFORM_ENGINEER_ROLE`、WHを `BCAST_PLATFORM_COMMON_WH` にします。
5. `numpy`、`pandas`、`scikit-learn`、`snowflake-snowpark-python`、`snowflake-ml-python` を利用できることを確認します。

DB `BCAST_PLATFORM_HANDSON` と `ML` スキーマは最初のコードセルで設定します。最初から全セルを一括実行せず、説明と出力を確認しながら上から1セルずつ実行してください。旧200台版のNotebookや表が残っている場合は、そのまま進めず、第1章の移行手順に従います。

NotebookのPython環境と共通WHは別の計算環境です。特徴量の集計と登録モデルの推論はWH、学習はNotebookのPython環境で行います。サービスに接続できない場合は管理者ロールへ切り替えず講師へ確認します。サービス作成時の待機タイムアウトは15分を選び、選べない場合は講師の案内に従います。

## 2. データと正解の範囲を確認する

視聴実績は `BCAST_PLATFORM_HANDSON.COMMON.VIEWING_DAILY`、ラベルは `BCAST_PLATFORM_HANDSON.RAW.DEVICE_LABELS` から読みます。対象期間は2026年5月1日〜7月31日、端末は `C000001`〜`C020000` の20,000台です。

| 対象 | 台数 | ラベル |
|---|---:|---|
| 全テレビ | 20,000 | 全台が視聴実績とラベル表に登場 |
| パネル | 2,000 | `LABEL_AVAILABLE = TRUE`、`TARGET_F1` は0または1 |
| パネルの正解1 | 343 | 合成世帯にF1層がいる |
| パネルの正解0 | 1,657 | 合成世帯にF1層がいない |
| 非パネル | 18,000 | `LABEL_AVAILABLE = FALSE`、`TARGET_F1 = NULL` |

**NULLは不明であり、0ではありません。** 非パネルは学習・評価に使いません。非パネルの隠れた正解や世帯構成は参加者用資材には含まれません。

入力は視聴ログ5ファイル、番組マスター、番組表、ラベルの計8 Parquetファイルです。番組マスターと番組表を用いて視聴を再生成しており、旧視聴ログの全行を保持した変換ではありません。正常な視聴区間は1,050,000件、RAWは検証用の重複・不正区間を含む1,050,648件です。

実際の配布データには、たとえば `C017281` がNW01を2026年5月13日22:34:17〜22:37:22に視聴した `NEWS` の記録があります。この区間は185秒、約3.0833分です。この端末は非パネルなので正解はNULLです。この1件から世帯属性を決めるのではなく、期間全体を集計してモデルへ渡します。

## 3. 1台につき12項目の特徴量を作る

共通マートをWHでテレビごとに集計します。約104万行の日次マートや約1,354万行の分展開データを、そのままNotebookへ持ってきません。収集は集計済み20,000行と小さなラベル表に限定し、上限超過検知用の1行を含めて各取得を最大20,001行に制限します。

| 列 | 意味 |
|---|---|
| `NEWS_SHARE` | ニュースの時間割合 |
| `DRAMA_SHARE` | ドラマの時間割合 |
| `VARIETY_SHARE` | バラエティの時間割合 |
| `ANIME_SHARE` | アニメの時間割合 |
| `SPORTS_SHARE` | スポーツの時間割合 |
| `MUSIC_SHARE` | 音楽の時間割合 |
| `MOVIE_SHARE` | 映画の時間割合 |
| `INFO_SHARE` | 情報番組の時間割合 |
| `TOTAL_MINUTES` | 全局・全対象日の総視聴時間（分） |
| `TOTAL_SESSIONS` | 正常な元視聴区間の件数の合計 |
| `ACTIVE_DAYS` | 視聴がある日数。複数局を見た同じ日は1日 |
| `MEAN_MINUTES` | 総視聴時間 ÷ 総視聴区間数 |

ジャンル割合は各ジャンルの時間を総時間で割り、8項目の合計が1になることを確認します。日次マートは各区間の実経過秒数を60で割った時間を、開始日の開始時ジャンルに全量計上します。番組境界で分割した厳密な番組別視聴時間ではありません。

モデルへの入力は表の順番の12列だけです。端末ID、正解、ラベル公開フラグ、世帯構成は含めません。IDは結果をテレビへ対応付けるために別に保持します。IDの欠損・重複・範囲違い、非有限な特徴量、ラベル契約の不一致は直さずに通過させるのではなく停止して確認します。

## 4. 固定モデルを学習し、評価結果を読む

端末ID順に並べたパネルを、`random_state=42`、`test_size=0.2`、ラベルによる層化分割で分けます。層化は、正解0・1の比率を両側で近づける方法です。

| 分割 | 全台数 | 正解0 | 正解1 |
|---|---:|---:|---:|
| 学習 | 1,600 | 1,326 | 274 |
| ホールドアウト | 400 | 331 | 69 |

同じテレビが両方に入っていないことを確認します。月別分割ではありません。同じ期間に観測した、学習未使用のテレビでの評価です。

使うモデルは `HistGradientBoostingClassifier(max_iter=100, max_leaf_nodes=15, l2_regularization=10, random_state=42)` です。複数の小さな決定木を順に学習し、誤りを補います。設定・データ生成規則・12列・分割・判定閾値0.5を評価前に固定しています。ホールドアウトの結果を見て再生成、特徴量選択、モデル選択、閾値調整をしません。別のロジスティック回帰や最適化は追加しません。

比較対象は `DummyClassifier(strategy='prior')` です。特徴量を使わず、学習データの正解1の比率274/1,600 = 0.17125を全台へ返します。これは実用モデルを追加するのではなく、学習モデルが単純な基準より良いかを確かめるための基準です。

### ローカル評価（参考）

以下は固定の配布データをPython 3.12.9 / scikit-learn 1.5.1でローカル検証した実測値です。後述のSnowflake上の評価とは別の結果であり、同じ数値とは扱いません。実際の演習ではセル出力を確認してください。

| 指標 | 学習モデル | 基準モデル | 読み方 |
|---|---:|---:|---|
| ROC AUC | 0.608477 | 0.500000 | 正解1を0より高く順位付けする能力。0.5が無差別の基準 |
| Average Precision（AP） | 0.217932 | 0.172500 | 確率順の適合率・再現率をまとめた指標。高いほどよい |
| Brier score | 0.148383 | 0.142745 | 確率と正解の二乗誤差。小さいほどよい |
| 適合率（precision） | 0.076923 | 0.000000 | 1と判定した中で、本当に1だった割合 |
| 再現率（recall） | 0.014493 | 0.000000 | 本当の1の中で、1と判定できた割合 |

基準モデルは閾値0.5で全件0になるため、正解1の検出はありません。適合率の分母が0のときは表示上0とします。APはホールドアウトの正解1の比率17.25%と比較します。

ローカル評価の学習モデルの混同行列は、行が正解、列が予測、いずれも0・1の順です。

| 正解 / 予測 | 予測0 | 予測1 |
|---|---:|---:|
| 正解0 | 319 | 12 |
| 正解1 | 68 | 1 |

**13台を1と判定して、正解は1台だけです。正解1の69台中68台を見逃しています。** 適合率7.69%、再現率1.45%であり、F1在籍の判定に十分とはいえません。全体の正解率だけを見れば320/400 = 80%ですが、すべて0と答える基準の82.75%より低く、不均衡なデータでは正解率だけを見てはいけません。

ROC AUCとAPには基準に対する順位付けの改善がありますが、Brier scoreは悪化しています。**確率予測全体の品質が基準を上回ったとはいえません。** 校正（確率の数値と実際の頻度を近づける処理）はしていないため、0.7を「同様の世帯の70%が正解1」と保証することはできません。Brierだけで校正誤差の原因を断定することもしません。

特徴量の説明には、ホールドアウトの1列を入れ替えてROC AUCの下がり方を見るPermutation Importanceを使います。説明専用であり、重要度を見て列を削除・再学習しません。負の値や小さい差は揺らぎも含み、因果関係や個人属性の証明ではありません。

## 5. 評価したモデルを登録する

登録先は `BCAST_PLATFORM_HANDSON.ML.TV_F1_PRESENCE_MODEL`、初期版は `V1` です。1,600台で学習して400台で評価したモデルそのものを登録し、2,000台や20,000台で学習し直しません。品質が低いことを承知した教材用の登録であり、本番採用の承認ではありません。

同名・同版が存在すると停止します。再実行する場合は `MODEL_VERSION` を未使用の `V2` などに変え、先頭から実行します。旧モデルの削除や既存版の上書きはしません。依存パッケージは学習時のscikit-learnの版に合わせ、推論先は `WAREHOUSE` に固定します。

新規利用者の環境に同名の登録版がなければ `V1` から始めます。講師の検証済み環境には既に `V1` があるため、その環境で再実行するときは未使用の `V2` を選びます。利用者が違っても同じ登録先を使う場合は既存版を確認してください。

確率を返す機能は `predict_proba` です。モデルの `classes_` が `[0, 1]` であることを確認し、0の確率・1の確率の順序と出力名を明示したシグネチャ（入出力の定義）で登録します。

`show_functions()` の出力で、登録した機能と入出力を確認してください。
推論セルでも返却列名を照合し、不一致なら保存へ進みません。戻った列を推測して0・1へ割り当てないためです。

## 6. 登録版で20,000台を予測する

Notebook内の学習済みオブジェクトを直接呼ぶのではなく、登録した版の `predict_proba` をWHで呼びます。0・1両方の確率が有限で0〜1に収まり、各行の合計が1になることを確認します。正解1の確率を `PROB_F1` とし、0.5以上を `PREDICTED_HAS_F1 = 1`、未満を0にします。

戻り値の行順だけで端末IDを付けると取り違える可能性があります。入力特徴量を保持するSnowpark入力を使い、戻った特徴量との照合で端末に対応付けます。同じ12項目の端末には同じ予測を対応付けます。特徴量や確率の欠落、行数・出力名の不一致は停止理由です。

全20,000台への推論には、学習1,600台、評価400台、非パネル18,000台が含まれます。全件の出力を新しい精度評価とは呼びません。評価値は学習から分離した400台に対する値のままです。

登録や推論の再実行時は以前の保存可能状態を無効にします。途中で失敗した処理の古い予測や、別のモデル版名を付けただけの予測は保存できません。

## 7. 保存を許可する

保存セルの初期値は次のとおりです。

```python
SAVE_RESULTS = False
```

このままでは確認メッセージで停止し、結果テーブルを書き換えません。**初回のここでの停止は意図した動作です。** ただし、モデル登録はこの前に実行されます。`False` はNotebook全体を読み取り専用にする設定ではありません。

1. 20,000台とモデル版の対応、確率の範囲、評価の限界を確認します。
2. 保存先の結果を置き換えてよいことを確認します。
3. 保存セルの `SAVE_RESULTS` だけを `True` にし、そのセルを実行します。

保存先は `BCAST_PLATFORM_HANDSON.ML.PREDICTIONS` です。履歴追加ではなく、既存の結果を置き換えます。元の視聴データとモデルを削除する操作ではありません。

| 列 | 内容 |
|---|---|
| `DEVICE_ID` | `C000001`〜`C020000`。欠損・重複なし |
| `PROB_F1` | F1在籍の未校正確率。浮動小数、0〜1 |
| `PREDICTED_HAS_F1` | 固定閾値0.5による整数0・1 |
| `MODEL_NAME` | 実際に推論したモデル名 |
| `MODEL_VERSION` | 実際に推論したモデル版 |
| `PREDICTED_AT` | UTCの保存時刻を `TIMESTAMP_NTZ` で保持 |

保存前に件数・ID集合・確率・閾値判定・モデル版の整合を確認します。
保存後は最大20,001行を読み戻し、20,000行であること、IDごとの確率・判定・モデル名・版・日時を照合します。
「20000台のF1予測を保存・照合しました」と表示されれば完了です。

`PREDICTED_AT` は視聴時刻ではありません。照合に失敗しても書き込みが自動で取り消されるわけではないため、第4章へ進まず講師に確認します。

## 8. Notebookの実行サービスを停止する

保存後、評価値・モデル版・必要な出力を記録してから、Pythonを動かしていたサービスを停止します。**画面を閉じるだけでは停止しません。** 同じサービスの別Notebookも切断され、変数や追加パッケージが失われるため、別作業が動いていないことを先に確認します。

1. Notebook上部の **Connected → サービス名 → Suspend（一時停止）** を選びます。
2. **SUSPENDED** とNotebookの切断を確認します。Shut down kernelだけで終わらせません。
3. 同じサービスで別作業がある場合は、講師と停止時点を調整します。

共通WHとNotebookサービスは別です。共有・システム管理のcompute pool自体は停止・削除しません。保存済みモデルと `PREDICTIONS` は残ります。短いWH自動停止設定だけではNotebookサービスが同時に止まるとは限りません。
