# 第3章 MLOps体験

第2章で、5局をまとめた分析用の表ができました。
この章では、その視聴履歴を使って「スポーツへの関心」を予測するモデルを作ります。

**学習するだけで終わらず、モデルに名前と版を付け、登録した版で予測して結果を残す**ところまで行います。
後から「この予測は、どのモデルで出したのか」を確認できるようにするためです。

> ラベルは教材用の架空の正解です。実在する人の関心・年齢・性別や、誰が視聴していたかを特定するものではありません。

## まず、何をするのか整理する

機械学習は、正解付きの例から傾向を学び、新しい入力に対する答えを予測する方法です。
この教材では「何をどれくらい見たか」をヒントに、架空の関心ラベル0・1を予測します。

| 言葉 | この章での意味 |
|---|---|
| 特徴量 | 予測のヒントにする数値。スポーツの視聴時間の割合など |
| ラベル | 答え合わせに使う正解。今回は関心なし0／関心あり1 |
| 学習 | 正解があるデータから、予測のためのルールを作ること |
| 評価 | 学習に使わなかったデータで、どの程度正解するか採点すること |
| 推論 | 学習済みのモデルを使って予測値を出すこと |
| Model Registry | モデルに名前・版・評価値を付けて保管する場所 |
| MLOps | モデルを作るだけでなく、版や利用結果を管理する取り組み |

ここでの「モデル」は、予測するための学習済みの仕組みです。
第2章のdbtモデル（表を作るSQL）とは意味が異なります。

```text
視聴実績 → 端末ごとのヒントを作る → 学習・採点
                                      ↓
                                名前と版を付けて登録
                                      ↓
                              登録した版で200台を予測
                                      ↓
                              予測値・モデル名・版を保存
```

## 1. Notebookを開く

1. 第2章で5局と共通マートのbuild・テストがすべて成功したことを確認します。
2. SnowsightのGit Workspaceで `notebooks/03_mlops.ipynb` を開きます。
3. 講師が案内するPython実行環境に接続します。ローカルPCにPythonを入れる必要はありません。
4. 画面の選択欄で実行ロールを `BCAST_PLATFORM_ENGINEER_ROLE`、WHを `BCAST_PLATFORM_COMMON_WH` にします。
5. 講師が案内するパッケージを利用できることを確認します。

DB `BCAST_PLATFORM_HANDSON` と `ML` スキーマは、最初のコードセルが設定します。
画面でDB・スキーマの選択欄を探す必要はありません。

パッケージは、Pythonで使う追加の道具です。このNotebookでは次を使います。

| パッケージ | 主な用途 |
|---|---|
| `numpy` / `pandas` | 数値や表データを扱う |
| `scikit-learn` | モデルの学習と評価 |
| `snowflake-snowpark-python` | SnowflakeのデータをPythonから操作 |
| `snowflake-ml-python` | モデル登録と登録版の利用 |

WorkspaceのPythonはcompute pool上で動きます。第1章のSQLでは準備されません。
接続できない場合は講師に確認し、管理者ロールへ切り替えて進めないでください。

サービス作成時の待機タイムアウトは15分を選びます。
選べない場合は講師が案内する値を使います。終了時の手動停止は第8節で行います。

## 2. 上から順に実行する

Notebookには「説明のセル」と「実行するコードセル」があります。
説明を読んでから、その下のコードセルを1つずつ実行してください。

前のセルで作った変数を次のセルで使うので、途中を飛ばすと動きません。
**最初から全セルを一括実行せず、出力を見ながら進めましょう。**
保存セルでは意図的に確認待ちで停止します。第7節で説明します。

| 段階 | 行うこと | 確認すること |
|---|---|---|
| 準備 | セッション・実行場所・モデル名と版を設定 | 指定ロール、共通WH、初期版V1 |
| 特徴量 | 端末ごとに視聴履歴を集計 | 200台、欠損・重複なし |
| 学習・評価 | 学習用80台と評価用20台に分割 | 同じ端末が両方に入っていない |
| 登録 | 評価したモデルをRegistryへ登録 | モデル名・版・評価値 |
| 推論 | 登録した版で200台を予測 | 端末と予測の対応、予測は0か1 |
| 保存 | 予測結果と使用した版を保存 | 200行を読み戻して照合 |

学習はNotebookのPython環境、端末集計と登録モデルの推論は共通WHで行います。
2つの計算環境の消費は別です。NotebookサービスをWHと混同しないでください。

## 3. モデルの入力を理解する

視聴実績は `COMMON.VIEWING_DAILY`、正解は `RAW.DEVICE_LABELS` から読みます。
元の視聴実績には、同じ端末が複数日・複数ジャンルに分かれて登場します。
それを **1端末につき1行のヒント**へまとめます。

- ニュース・ドラマ・バラエティ・アニメ・スポーツの視聴時間の割合：5項目。
- 総視聴時間と総視聴回数：2項目。

たとえば、総視聴時間100分のうちスポーツを30分見た端末なら、スポーツ割合は0.3です。
このような数値を7項目並べて予測に使います。この100分・30分は説明用の例です。

端末IDは結果を対応付けるためのキーです。端末IDや正解ラベルそのものはモデルの入力にしません。

200台のうち、正解があるのは100台で、0と1が各50台です。
正解のない残り100台は、学習や採点には使いません。不明を0に置き換えないでください。

正解がある100台を、学習80台・評価20台へ分けます。
同じ端末が両方に入らないようにし、両方に0と1が含まれるように分割します。

✅ 特徴量は200台分、学習は80台、評価は20台になっていることを確認します。

## 4. 評価結果を読む

今回のモデルは **決定木**です。数値の条件で分岐しながら答えを決める仕組みです。
学習では、どの特徴量のどの条件で分けると正解に近づくかを決めます。

比較のため、「常に多数派のクラスを答えるだけ」の単純なモデルも用意しています。
どちらも同じ評価用20台で採点し、ヒントを使う意味があったかを見ます。

| 表示される指標 | 読み方 |
|---|---|
| accuracy | 全体で正解した割合。たとえば20台中12台なら0.60 |
| balanced accuracy | 正解0の端末と正解1の端末、それぞれの正解率を平均した値 |

上の12台は計算方法の説明例です。実際の結果はNotebookの出力を確認してください。

大切なのは **学習に使っていない端末で採点すること**です。
既に学習した例だけで採点すると、新しいデータでも当たるかが分かりません。

後で行う全200台への予測には、学習済み端末も含まれます。その全件で精度を評価し直すことはしません。
教材の点数を、実際の視聴者への予測精度として扱わないでください。

## 5. モデルを登録する

登録先は `BCAST_PLATFORM_HANDSON.ML.SPORTS_INTEREST_MODEL`、初期版は `V1` です。
学習・評価したモデルそのものと、評価値を登録します。ここで全100台を使って学習し直すことはしません。

版を付けると、後から別の学習をしたときも、V1とV2を区別できます。
✅ 登録セルの出力で、モデル名・版・評価値を確認してください。

**同名・同版が既にあると停止します。** 以前のモデルを上書きしないためです。
再実行する場合は、初期設定セルの `MODEL_VERSION` を `V2` など未使用の版へ変え、上から実行します。
以前のモデルを削除して通す手順ではありません。

学習時と同じscikit-learnの版を指定し、ウェアハウスで予測できる形に登録します。
必要なパッケージを利用できないエラーが出たら、指定を外して進めず講師へ確認します。

## 6. 登録したモデルで予測する

登録セルが返したモデル版の `predict`（予測する機能）を使います。
Notebook内にある学習直後のモデルではなく、**登録先から呼び出したモデルで予測できるか**を体験する手順です。

予測値は0か1です。1が「関心ありの予測」、0が「関心なしの予測」を表します。
確率ではないので、1を「100%確実」と読むことはできません。

入力の特徴量と予測を照合して、200台の端末へ対応付けます。
行の並び順だけで端末IDを付けると取り違える可能性があるため、その方法は使いません。
予測の欠落や0・1以外の値があると停止します。

✅ 200台分の予測がそろい、端末と結果の対応確認が成功していることを確認します。

登録や推論をやり直すと、以前の予測はそのまま保存できなくなります。
モデル版を変更した場合も、上から順に実行してください。古い予測へ新しい版名だけを付けないための確認です。

## 7. 保存を許可する

保存セルの初期値は次のとおりです。

```python
SAVE_RESULTS = False
```

このままでは確認メッセージとともに停止し、結果テーブルを書き換えません。
**初回にここで止まるのは、意図した動作です。**

1. 推論まで成功したことを確認します。
2. 保存先にある予測結果を置き換えてよいか確認します。
3. 保存セルの `SAVE_RESULTS` を `True` に変更し、そのセルを実行します。

モデル登録は、この保存確認より前に実行済みです。
`False` はモデル登録も含めて何も変更しない設定、という意味ではありません。

保存先は `BCAST_PLATFORM_HANDSON.ML.PREDICTIONS` です。履歴の追加ではなく、テーブル内容を置き換えます。

| 列 | 内容 |
|---|---|
| DEVICE_ID | 端末ID |
| PREDICTED_SPORTS_FAN | 予測クラス0または1 |
| MODEL_NAME | 使用したモデル名 |
| MODEL_VERSION | 使用した版 |
| PREDICTED_AT | UTCでの保存時刻 |

保存後、Notebookはテーブルをもう一度読み、端末・予測値・モデル名・版が合うか確認します。
**「200台の結果を保存・照合しました」** と表示されれば保存完了です。

`PREDICTED_AT` はUTCの保存時刻です。視聴記録の時刻や、推論開始時刻ではありません。
照合が失敗しても保存は自動で取り消されないので、第4章へ進まず講師へ報告してください。

## 8. Notebookの実行サービスを停止する

保存が終わったら、Pythonを動かしていたサービスを停止します。
**画面を閉じるだけでは止まらないため、この操作まで行って第3章は完了です。**

停止すると、同じサービスにつないだ別のNotebookも切断されます。
メモリー内の変数や追加パッケージ等も失われるので、別の作業が動いていないか先に確認します。
必要なファイルをWorkspaceへ保存し、評価値・モデル版・必要な出力を記録しておきましょう。

1. Notebook上部の **Connected** を開き、接続中のサービス名にカーソルを合わせて **Suspend（一時停止）** を選びます。
2. サービスが **SUSPENDED** になり、Notebookが切断されたことを確認します。**Shut down kernelだけ**で終了せず、サービスの停止まで確認します。
3. 同じサービスで別作業がある場合は、講師と停止時点を調整します。

共通WHとNotebookサービスは別です。共有・システム管理のcompute pool自体は停止・削除しません。
**保存済みのモデル・PREDICTIONSは残ります。** 第4章のアプリからは、保存済みの結果を利用できます。

サービスの待機タイムアウトの既定値は24時間です。
短いWH自動停止を設定していても、Notebookサービスが同時に止まるわけではありません。

出典: [Notebookサービスの停止と費用](https://docs.snowflake.com/en/user-guide/ui-snowsight/notebooks-in-workspaces/notebooks-in-workspaces-compute-setup)

## 振り返り

学習して終わりではなく、「採点する」「版を付ける」「その版で予測する」「結果と版を残す」までを体験しました。
これにより、後で予測結果を見たときに、使ったモデルを追跡できます。

自動での再学習や、データの傾向が変わったことを検知する監視は、この演習には含めていません。
本番の精度を保証するものでもありません。
