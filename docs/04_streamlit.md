# 第4章 視聴実績と予測をグラフで見る

第2章で分析用の表、第3章で予測結果ができました。
この章では、それを **期間や放送局を選んで見られる画面**にします。

使うのはStreamlitです。Pythonでグラフや入力欄を作る仕組みで、教材のコードは用意してあります。
受講者は3つのファイルを配置し、画面を動かして、閲覧用ロールからも使えることを確認します。

**本編では「経路B：ウェアハウスで動かす方法」だけを行います。**
末尾の経路Aは補足です。両方を続けて作る必要はありません。

## 画面で何ができる？

| 画面の場所 | できること |
|---|---|
| 左側の条件欄 | 視聴期間と放送局を選ぶ |
| 「視聴実績・推移」タブ | リーチ、視聴時間、視聴回数、日別推移や内訳を見る |
| 「スポーツ関心の予測」タブ | 第3章で保存した0・1の予測結果を見る |
| 「再読込」ボタン | 保持している集計結果を捨て、最新のデータを読み直す |

第3章がまだ終わっていなくても、実績画面は使えます。
予測は、その結果が保存されてから表示できるようになります。
このアプリ自身が学習や予測を行うわけではありません。

## 1. 作成前に確認する

- 第2章の5局とcommonのbuild・テストが完了している。
- 作成用ロール `BCAST_PLATFORM_ENGINEER_ROLE` を使える。
- `COMMON.VIEWING_DAILY` と共通WHを利用できる。
- 第3章を終えている場合は、予測保存・照合とNotebookサービス停止まで済んでいる。

同名の `VIEWING_APP` が既にある場合は、その用途を講師へ確認します。
別の作成方法で既存アプリを上書きしないでください。

### 配置する3ファイル

| ファイル | 役割 |
|---|---|
| [streamlit_app.py](../app/streamlit_app.py) | 画面の入口。ボタン・条件欄・グラフを作る |
| [queries.py](../app/queries.py) | データを集計するSQLをまとめたファイル |
| [environment.yml](../app/environment.yml) | 必要なPython・パッケージの指定 |

3つとも、アプリの同じフォルダに置きます。
入口だけ配置すると、集計SQLのファイルが見つからず起動できません。

> ⚠️ アプリは所有者の権限でデータを読みます。
> 共有すると、閲覧者はアプリ所有者が取得した結果を見ることになります。
> 所有者は `ACCOUNTADMIN` ではなく教材のエンジニアロールにします。

利用者ごとに行を出し分ける機能は実装していません。
共有する結果は教材データに限定し、正解ラベルを画面へ追加しないでください。

## 経路B：ウェアハウスで動かす（推奨・本編）

### 2. アプリの作成画面を開く

Snowsightの **Projects → Streamlit** を開きます。
**Run on warehouse** を選べることを確認してください。

warehouse runtimeとは、PythonのアプリとSQLをウェアハウスで動かす方式です。
この手順では共通WHを使い、Notebook用のcompute poolをアプリへ指定しません。

作成方法は、表示されるメニューに合わせて次のどちらかを使います。

### 方法① Gitリポジトリから取り込む

`+ Streamlit` 横のメニューに **Create from repository** があり、WHでの実行を選べる場合の方法です。

| 項目 | 指定する値 |
|---|---|
| リポジトリ | `BCAST_PLATFORM_HANDSON.INTEGRATIONS.BCAST_PLATFORM_REPO` |
| ブランチ | 講師指定の公開済みブランチ。通常は `main` |
| 入口ファイル | `app/streamlit_app.py` |
| アプリ名 | `VIEWING_APP` |
| 配置先DB | `BCAST_PLATFORM_HANDSON` |
| 配置先スキーマ | `MART` |
| Query warehouse | `BCAST_PLATFORM_COMMON_WH` |
| App warehouse | `BCAST_PLATFORM_COMMON_WH` |

作成後のファイル一覧で、`queries.py` と `environment.yml` も入口ファイルと同じフォルダにあるか確認します。
リポジトリの取り込み範囲によって不足する場合は、教材の対応ファイルを追加してください。

### 方法② 新規アプリにファイルを配置する

上のメニューがない場合は、**Projects → Streamlit → + Streamlit App** から作成します。

1. **Run on warehouse** を選びます。
2. アプリ名・DB・スキーマ・WHに、方法①の表の値を指定します。
3. エディタの `+ Add → Upload file`、またはファイル編集で、教材の3ファイルを同じフォルダへ配置します。
4. Git Workspace内の教材ソースを使い、初期表示されたデモコードを教材コードへ置き換えます。

Git Workspaceから内容をコピーして配置する方法でも構いません。
Streamlit側の編集がGitHubへ自動反映されるとは限りません。この章でcommit・pushする必要はありません。

**Run on warehouseが選べない場合は、講師へ確認して停止します。**
準備なしに別の実行方式へ切り替えないでください。

### 3. パッケージを確認してRunする

このアプリは、Python 3.11、Streamlit 1.50.0、pandas 2系、Snowparkを使います。
`environment.yml` とPackages欄を確認し、利用できない指定があれば講師へ確認します。

**Run** を選びます。通常のPythonワークシートではなく、Streamlitの実行ボタンを使ってください。
画面上部に **「5局の視聴データ」** が表示されたら、次へ進みます。

## 4. 実績のグラフを確認する

左側で全5局と、2026年7月1日〜30日を選びます。
「視聴実績・推移」タブで、3つの数値を確認しましょう。

| 指標 | 意味 | 全期間・全5局の期待値 |
|---|---|---|
| 期間全体のリーチ | 1回以上視聴した端末を、重複なしで数えた台数 | 200端末 |
| 総視聴時間 | 視聴分数の合計 | 画面表示は約667,632.9分 |
| 総視聴回数 | `SESSION_COUNT` の合計 | 18,000回 |

### なぜ、局別リーチを足してはいけない？

たとえば同じ1台がNW01とNW02を見た場合、各局のリーチはそれぞれ1台です。
しかし、両局をまとめたリーチは2台ではなく **1台**です。

このためアプリは、選択範囲全体で端末IDの重複を除いて数え直しています。
日別・局別・ジャンル別のリーチを足して、全体のリーチにはしません。
ここでの単位は端末であり、人数や世帯数でもありません。

### 条件を変えてみる

1. NW01だけを選び、日別グラフと局別内訳が変わることを確認します。
2. 1日だけ、または数日間を選び、表示期間と数値を確認します。
3. 局の選択をすべて外し、「放送局を1つ以上選んでください」の案内が出ることを確認します。
4. 日付の片方だけを選んだ状態では、開始日・終了日を選ぶ案内になることを確認します。

視聴回数には表の行数ではなく、集計済みの `SESSION_COUNT` を使います。
第2章の「2行・3回・1端末」の例を思い出してください。

## 5. 予測結果を見る

「スポーツ関心の予測」タブで **「予測結果を表示」** にチェックを入れます。
チェックするまでは、予測テーブルへ問い合わせません。

表示される0・1の内訳、モデル名、バージョンを、第3章の出力と比べます。
予測あり・予測なしを合わせた端末数が、同じ条件の実績リーチと一致することも確認してください。

### 予測画面の注意点

- 予測1は「関心ありの予測」、0は「関心なしの予測」です。確率や実測した属性ではありません。
- 期間や局を変えると、その条件で視聴した端末が対象になります。学習期間を変更したり、再学習したりする操作ではありません。
- モデル名・版・保存日時を併記します。日時は **UTCの保存時刻**であり、推論開始時刻ではありません。
- 同じ端末が複数日・複数局に現れても、対象端末を重複なしにしてから予測と結び付けます。

### 案内やエラーが出たら

| 表示の状況 | 意味・確認すること |
|---|---|
| 予測が未作成、または参照権限なし | 第3章の保存と作成用ロールの参照権限を確認 |
| 予測テーブルが空 | 第3章で200台の保存・照合が成功したか確認 |
| 「予測なし」の端末がある | その端末に対応する保存済み予測がない |
| 重複・欠損・不正なクラス | 不正確な内訳を出さないため表示を止めている。第3章の結果を確認 |
| Snowflakeとの接続切れ | アプリを再起動して再接続。未作成やゼロ件という意味ではない |

予測に問題があっても、実績画面は別に利用できます。
データを更新した後は「再読込」を選びます。これは最新結果の再取得であり、データ更新やモデル再学習ではありません。

## 6. 作成後の共有と公開確認

作成者の画面で動くだけでなく、閲覧用ロールで使えることを確認します。

1. **Projects → Streamlit** で `BCAST_PLATFORM_HANDSON.MART.VIEWING_APP` を開きます。
2. DB・スキーマ・アプリ名と、所有者が `BCAST_PLATFORM_ENGINEER_ROLE` であることを確認します。
3. **Share／共有**で `BCAST_PLATFORM_ANALYST_ROLE` に閲覧用の `USAGE` を付与します。
4. UIに **Publish／公開** があれば、意図した版を確認して公開します。
5. Projects → Streamlitから共有用の閲覧画面を開き直し、実績・フィルター・予測を確認します。

`USAGE` は、そのアプリを使うための権限です。編集権限や所有権を渡す操作ではありません。
**共有先に `PUBLIC` を指定しないでください。**

単独学習ではアナリストロールで確認します。
他の強い権限が同時に有効だと、アナリスト権限だけで見られたか判断できないため、講師の案内に従って確認します。
別ユーザーで見る場合は、その利用者にアナリストロールが付与されている必要があります。

所有者のエディタでのRunと、閲覧者への公開は別です。
閲覧用ロールで確認できなければ、共有まで成功したとは判断しません。

### 権限の補足

第1章で、作成ロールにはDB・MART・COMMON・共通WHの利用権限と、MARTへのアプリ作成権限を準備しています。
共通マートを読む `SELECT` も必要です。
予測表示時は、所有者がMLスキーマとPREDICTIONSを参照できる必要があります。

閲覧者にはアプリのUSAGEのほか、DB・MART・共通WHのUSAGEが必要です。
アプリ共有のためにRAWや正解ラベルを直接公開しないでください。

## 経路A：Git Workspaceで開発する（補足）

**経路Bを完了した方は、ここを実行する必要はありません。**
Workspaceで開発アプリを動かす方式を試したい場合だけ、講師の案内で使います。

この方式では、Pythonを動かすcompute poolが別途必要です。
共通WHはSQLの実行担当であり、compute poolを兼ねません。
第1章のSQLだけでは、この方式の準備は完了しません。

### 開発して公開する流れ

1. 新教材のGit Workspaceで `app/streamlit_app.py` を開きます。
2. Streamlitの設定作成が案内されたら、入口と、同じフォルダの `queries.py` を確認します。
3. 案内がない場合は `+ Add new → Streamlit app` で作ったフォルダに、教材のPython2ファイルを配置します。元の教材ファイルを上書きしません。
4. Settings／ExecutionでSQL用WHを `BCAST_PLATFORM_COMMON_WH` にします。
5. 講師が指定するcompute poolと、その利用権限を確認します。既定WHが必要な場合も、ユーザー設定を勝手に変更しません。
6. Streamlitの **Run** で開発用の画面を起動し、本編の表示確認を行います。
7. **Deploy** で `BCAST_PLATFORM_HANDSON.MART.VIEWING_APP` へ公開し、共通WHとcompute poolを確認します。
8. 本文の「6. 作成後の共有と公開確認」に戻り、閲覧者向けの版を確認します。

Runは私用の開発画面、Deployは他の利用者へ公開する操作です。
Deploy時に共有先を選ぶ場合も、アナリストロールだけを指定します。

### この方式のパッケージ設定

ランタイムに組み込まれた `streamlit`、`pandas`、`snowflake-snowpark-python` を使います。
`environment.yml` はWH用なので、コンテナ方式の依存設定には使いません。

コンテナ用の `snowflake.yml` は配布していません。
画面が作る設定を講師と確認し、`pyproject.toml` が生成された場合は、パッケージ取得先やネットワークの前提も確認します。
教材アプリ自体は、外部API・画像・フォント・CSSを取得しません。

画面で検出・設定生成・Deployの項目が異なる場合は、その場で確認します。
未確認のCLI手順へ切り替えて進めないでください。

## 補足：コードの中の工夫

- 日付・局の値はSQLへ直接つなげず、バインド変数として渡します。入力とSQLの命令を分けるためです。
- 集計結果は60秒間キャッシュ（一時保存）し、同じ問い合わせを減らします。
- 予測データの検査と表示用集計は1つのSQLで取得し、一緒にキャッシュします。古い検査結果で新しい予測を判定しません。
- データ取得のエラーを「視聴ゼロ」として表示しないよう、メッセージを分けています。
