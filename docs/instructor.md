# 講師用：実行順と事前確認

## 公開前のゲート

- GitHubの公開範囲とpushを承認してから新リポジトリを公開する。旧リポジトリのremoteや履歴は変更しない。
- 配布するコミットを固定し、Git-backed Workspaceとデータ取込用Git参照が同じ版であることを確認する。
- 実機検証は教材用トライアルに限定。業務用アカウントに教材DDLを実行しない。
- 開始前に新DB・専用WH・専用ロールが既に使われていないか確認する。旧環境を削除して空けない。
- WarehouseとNotebookの実行環境、MLパッケージ提供、Cortex利用可否を確認する。compute poolはWHとは別管理。

## 当日の必須チェックポイント

1. RAW：5局各3,600行、ラベル200行。Parquetの型とzstd圧縮は事前監査済みの配布物を使う。
2. dbt：各局2モデル＋7テスト、5局すべて成功後に共通1モデル＋3テスト。計11モデル＋38テスト。
3. 実行履歴：局別モデルとテストが対応するWHで、統合だけが共通WHで実行されたことを確認する。
4. Notebook：200端末、既知100台、学習80台・評価20台。V1既存時は停止し別版を選ぶ。SAVE_RESULTSの意図的な停止を説明する。
5. ML結果：200行、端末重複なし、予測0/1、実際に使用したモデル名・版・UTC保存日時を確認する。
6. Streamlit：所有者のRunだけで終えず、公開したアプリをアナリストロールで閲覧する。予測未作成でも実績画面は動くこと。
7. SV→Agent：Searchなしで局・日・ジャンルの指標を質問できること。異なる局の日別リーチ等を単純加算しないこと。
8. CoWork：既定ロールがAgentと道具の権限を持つことを確認する。ユーザー既定値を一括で書き換えない。

## GUIと保険SQLの比較

同じ正規オブジェクト名を使う。作成済みGUI版を無断で置換しない。設定を取得して指示文・参照先・実行予算・WH・モデル設定・所有者・権限を比較する。実体を比較できていない場合は未検証と記載する。LLMの回答文章が毎回同じことは合格条件にしない。

## 補足へ回すもの

基本SQL・任意Search・スケジュール・詳細監視は本編の前提にしない。App Runtimeは講師の既存デモのみ。必須操作の実測と質疑を含めて3時間の枠に収まるか確認し、収まらなければ説明や補足を減らす。

## 片付け

開発アプリを停止してから、保持するモデルや結果を確認する。cleanupは新教材だけを対象とし、共有compute poolを消さない。新しいモデル版やユーザーが追加したオブジェクトがある場合は、DB全体削除前に必ず確認する。
