## 1. 基本SQLで、集計の意味を確かめる

[01_basic.sql](01_basic.sql) を開き、1文ずつ実行します。
データを作成・更新・削除するSQLではありません。

冒頭の `USE` は、この作業で使うロール・DB・WHを選びます。
ユーザーの既定値を変更するものではありません。
最初のSELECTで、アカウント・ロール・DB・WHが教材用であることを確認してください。

### ジャンルごとの実績を集計する

第2章で5局とcommonのbuild・テストが完了してから、ジャンル別集計のSELECTを実行します。
対象は2026年5月1日〜7月31日です。共通表の6列は `NETWORK_ID`、`DEVICE_ID`、`VIEW_DATE`、`GENRE`、`SESSION_COUNT`、`VIEW_MINUTES` です。
端末IDは `C000001`〜`C020000`。再生成した合成データであり、旧ログの行をそのまま保存したものではありません。
ジャンルはNEWS（ニュース）、DRAMA（ドラマ）、VARIETY（バラエティ）、ANIME（アニメ）、SPORTS（スポーツ）、MUSIC（音楽）、MOVIE（映画）、INFO（情報）の8種類だけです。この8種類以外は不正値として扱います。
各視聴区間の時間は開始日と開始時のジャンルに計上します。番組単位の正確な視聴時間ではありません。

V2配布データのローカル期待値は、全5局・全期間のリーチ20,000台、総視聴回数1,050,000回、総視聴時間約12,511,642.266667分です。V2の本編SQLとの照合、この補足SQLとSearchの実機実行は未検証です。

| SQL内の計算 | 意味 |
|---|---|
| `COUNT(DISTINCT DEVICE_ID)` | 同じ端末を何度も数えず、視聴した端末数を求める |
| `SUM(SESSION_COUNT)` | 集計表に残した視聴回数を足す |
| `SUM(VIEW_MINUTES)` | 視聴分数を足す |
| `GROUP BY GENRE` | ジャンルごとに分けて計算する |

✅ ジャンル別にリーチ・視聴回数・視聴時間が表示されることを確認します。
ジャンルをまたいで見る端末があるので、ジャンル別リーチを足して全体リーチにはしません。

### 同じSQLの結果を再利用する仕組み

**結果キャッシュ**は、条件が合えば以前のSQL結果を再利用し、計算を省く仕組みです。
先ほどの共通マートのSELECTを、SQLの文字列・ロール・設定・入力データを変えずに2回実行してみます。

Snowsightのクエリ履歴とプロファイルで、結果再利用の表示や実行内容を確認します。
2回目が速かったというだけでは、結果キャッシュが使われた証拠にはなりません。
表示を確認できなければ、再利用されたとは断定しないでください。

> 💡 結果キャッシュは、条件がそろっても必ず使われるわけではありません。
> `USE_CACHED_RESULT` が無効なら、この観察は省略します。設定変更は不要です。

WH内に読み込まれたテーブルデータを再利用するキャッシュとは別です。
また、`RESULT_SCAN` で過去結果を読むことも、同じSELECTが自動で再利用された証明にはなりません。
この教材のデータ量で、本番の性能や削減率を評価することはしません。

## 2. 視聴区間をまとめる

`from-to` は「開始から終了まで」の区間を指します。
たとえば、同じ端末が同じ局・同じジャンルを次のように記録していたら、どう扱うでしょうか。

```text
08:00 ───────── 08:30
          08:25 ─────── 08:40

重なりを1つの区間にまとめると
08:00 ───────────────── 08:40
```

この補足では、重なる区間と、終了・開始がぴったり接する区間をまとめます。
視聴していない空白時間は埋めません。

### 操作と結果

`01_basic.sql` 末尾の `WITH fixture ...` から始まるSQLを実行します。
SQL内に説明用の7行を直接用意しているので、原本のテーブルへ書き込むことはありません。
共通マートがなくても、第1章のセットアップ後なら、この文だけを実行できます。

| まとまった区間 | 元の行数（`SOURCE_ROWS`） |
|---|---|
| 08:00〜08:50 | 4行 |
| 09:00〜09:20 | 2行 |
| 10:00〜10:05 | 1行 |

✅ 出力は3行です。各行の `INPUT_ROWS = 7`、`FOLDED_ROWS = 3` も確認します。

### なぜ「直前の1行」だけと比較しない？

長い区間の内側に短い区間があると、直前の終了時刻だけでは、まだ長い区間が続いていることを見落とします。
そのためSQLでは、**それまでの行の中で最も遅い終了時刻**と比較しています。

区間は開始を含み終了を含まない `[VIEW_FROM, VIEW_TO)` として扱います。
そのうえで、端末・局・ジャンルが同じで、接している区間も1つへまとめるルールです。

これは、まとめ方を学ぶための専用サンプルです。`C000001` も説明用で、本編の同じIDの履歴とは結合しません。
本編データに重複があるという意味でも、本編の視聴回数・視聴時間の定義を変更する操作でもありません。
不正時刻、NULL、異なる局の競合解決、日付境界での分割は扱いません。

## 4. 毎日自動で動かすなら？

本編では、各局の処理が成功したことを人が確認して、commonを実行しました。
定期実行にするときも、「毎日ある時刻に起動する」だけでは十分ではありません。

```text
今回分のロード成功
       ↓
今回分の5局の作成・テストがすべて成功
       ↓
commonの作成・テスト成功
       ↓
グラフや後続処理で新しい実績を使う
```

**ここではスケジュールを作成・有効化しません。** 次の点を考える補足です。

1. 入力データとコードの版をそろえます。同じ一連の実行中には入力を更新しません。
2. `nw01`〜`nw05`を、それぞれのtarget・選択範囲・局別WHでbuildします。
3. 同じ実行回の5局が、モデル・テストともに成功した場合だけcommonをbuildします。
4. commonも成功してから、後続の処理に新しい実績を使わせます。
5. 失敗通知、やり直し、二重起動の防止、停止担当を決めます。

昨日の成功や、以前作ったテーブルが残っていることを、今日の成功と混同してはいけません。
テスト失敗時にも作成済みテーブルは残るので、合格前の成果物を利用者へ見せない切替方法も設計が必要です。

dbtの呼び出しごとの成功記録と、やり直す場合の入力版を管理します。
commonで `+` を付けて局別まで選ぶ、あるいは対象指定なしで全体を実行する方法には変えません。

現在の補助macroはtarget・選択範囲と、今回選んだモデル・テストの結果を調べます。5回分の成功記録や二重起動の防止など、全体の実行管理は行いません。
MLの再学習・登録・推論は別途判断する処理で、毎回自動学習する前提ではありません。
固定文書を検索する補足Searchも、この実績更新の流れには加えません。
